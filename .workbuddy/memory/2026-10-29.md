
# 2026-10-29

## v0.20.0：多快照合并 + 数据按店铺分目录 + 手动导数据两模式

用户提的四个需求（都是「同一天反复取数、反复试算」场景下的实际痛点）：
1. 多次取不同区间后，只按最新那份算 → 要能**合并指定的多份**
2. 默认算最新，但可以选择是否合并之前的数据
3. 自动抓的数据按店铺分开管理
4. 手动去店铺导数据的功能没做

### 一、多快照合并

`src/loader.py` 新增 `load_from_dirs(folders, ...)`，`load_from_dir()` 变成它的包装。
逐目录解析后按类型合并去重：

- 订单：键 = **订单号 + SKU**，跨文件冲突时**靠后的目录覆盖靠前的**
  （调用方把目录按取数时间从旧到新排，所以「后取」= 最新）
- 广告/联盟：`_merge_same_kind()` 整行去重；额外统计「同商品+同日期但金额不同」
  的行数，>0 就写进 issues 提醒（防区间重叠时重复计入）
- 映射：全量合并（老规矩）

**踩到的坑（重要）**：订单金额按「订单内 SKU 行数」分摊到每一行，而行数是
`parse_orders` 在**每份文件内部**统计的。一个订单的 3 行被切在两个快照里时，
各算各的是 1 行和 2 行 → 分摊基数错 → 买家实付和交易手续费都偏。
**合并后必须重算 `order_line_count`**。修完实测：合并两份各 693 行的快照 →
GMV 13074.78 / 订单 796 / 行 1386，与「整份 1386 行单独算」完全一致
（修之前净利差 0.7）。

### 二、店铺分目录

`src/paths.py`：`store_kind_dir(shop_id, kind)` / `unknown_dir()` / `kind_dirname()`
（统一 order→orders 这类命名差异，之前 _unknown 里冒出 order/ 和 orders/ 两种目录）。

- 上传时**靠表头**判断类型（`classify_rows`），不靠文件名
- 认不出店铺 → `data/stores/_unknown/<时间戳>/` + 回报 warning，**不再静默落公共目录**
- 选了店铺却没数据 → 直接报错，不悄悄拿别的数据算
- `scripts/adopt_legacy.py` 一次性认领公共目录里的历史文件

### 三、手动导数据两模式

扩展面板新增「手动导数据」区 + 模式开关：
- 陪同导出：`chrome.downloads.onChanged` 监听下载完成 → `downloads.search` 拿 url
  → 后台 fetch 回来 → 上传桥（manifest 已有 downloads 权限，fetch 能带 cookie 下 CDN 文件）
- 只开页面：只 `chrome.tabs.create` 跳后台

桌面端手动导入按**所选国家**的列标题认表（`classify_rows(rows, aliases)` 新增 aliases 参数），
回执写明「按 XX 的列标题识别」。

### 四、值得记住的技术点

1. **UI 里 `$` 是 `document.querySelector`（选择器带 #），不是 getElementById。**
   写 DOM 桩时按 getElementById 写会得到「元素找不到」的错误结论。
   教训：`scripts/check_snap_ui.js` 的桩必须跟真实实现语义一致，否则测了等于没测。
2. `Path.relative_to()` 在 Windows 上是**反斜杠**分隔，`split("/")` 切不开 →
   子目录分类要用 `rel.parts[0]`。
3. CSV 行数要用 `csv.reader` 数「记录条数」，直接数物理行会把字段里的换行算成多行
   （实测虚高 16 行）。
4. `bridge/ui.py` 里内嵌的 JS 可以用正则提取出来跑 `node --check`，
   扩展的 JS 用 `node --check` 同样有效——改完 UI 必查，比肉眼看靠谱。

### 遗留

- 截图工具在本环境一直报「exceeds the 10 MiB image limit」（即使 clip 很小），
  界面验证只能靠 DOM 桩 + 接口验证
- 广告 / 联盟 / 链接资料三类数据仍未在真实店铺跑过
- 其余 9 个国家费率、订单服务费仍是占位值

## 11:50 v0.20.1：预设系统（口径一键切换 / 按店铺分设）

用户提的需求：所有配置（参数、费率等）都能保存为预设，可设全局预设 + 各店分开预设。

### 实现

`src/presets.py`（新增）：
- 两级作用域：`global`（所有店铺）/ `shop:<店铺ID>`（只对那家店，优先级更高）
- 一份预设装：params（含每项 kinds）、formulas、order_fields、cost_fields、
  exclude_zero_amount、（可选）rates（按国家合并，不整体替换）
- **内置预设只改 kinds**（kind_overrides），公式与列标题保持原样
  → 套用模板口径不会冲掉用户手改的公式；自定义预设才是完整快照
- 应用前自动备份到 `config/_backup/`（留最近 20 份），可回滚

`bridge/presets_api.py` + server.py 路由：`/api/presets` 及 save/apply/delete/update/rollback。
`bridge/ui.py`：计算参数页与费率页各加一块预设区（id 前缀 ps / pr），共享同一套逻辑。

内置三个预设：
- 默认 5 条口径（用户 2026-10-29 确认的那五条）
- 模板口径（AE2=0）
- 去 0 元样品（等同打开总开关）

### 关键验证

**应用「模板口径（AE2=0）」后，程序默认配置与模板逐条 51 条链接完全一致**
（GMV / 买家支付总额 / 分摊订单数 / 交易手续费，0 条不一致）。

这个验证有个巧劲：verify_vs_template.py 是用「脚本内 ALIGN 覆盖」来对齐模板的；
而预设验证是「先套预设、再用程序默认配置跑」，走的是完全不同的路径，两边结果一致，
说明预设改的口径和模板逻辑真的对上了。

### 用户口径确认（v0.20.0 时的默认配置就是对的，无需改）

1. GMV 不算取消和退货退款 → kinds ['normal','zero_amount']
2. 商品成本 不算取消和退货退款 → ['normal','zero_amount']
3. 发单费 不算取消 → ['normal','refunded','zero_amount']
4. 交易手续费 不算取消/退货/样品 → ['normal']
5. 订单服务费 不算取消和样品 → ['normal','refunded']

**样品总开关不会跟默认参数打架**：它只做「再收紧一层」——把已勾了 0元样品 的项
一律剔掉；本来就只勾 normal 的项（交易手续费）不受影响。

### 顺带查清的事

- 模板 AE2 是「净利润」页右上角 AE1='0是去除样品' / AE2=0 的手工开关，156 处公式引用它
- AE2 只影响 D/E/G 三列；因为 0 元样品单的 Order Amount=0，
  它实际上只改变订单数/件数和成本，买家支付总额与交易手续费两档完全相同
- 模板 AE2=0 档的买家支付总额**含取消退货**，订单数却不含 —— 模板自身口径不统一；
  程序里这两项各自独立勾选，更可控

### 公式中文化（核心）

`src/formula.py` 加 `BUILTIN_CN`（订单数/件数/买家实付/GMV/成本单价…）、
`DEFAULT_RATE_CN`（平台佣金/交易手续费/人民币汇率…）、`rate_aliases(labels)`。
`compile_expr` 增加 aliases 参数，**先替换中文别名再替换裸标题**——
顺序反了的话「订单数」会被当成订单表的列标题。

费率项中文名存在 `rates.json` 的顶层 `labels` 段（字段级，不是国家级），
费率页新增「费率项的中文名」表来编辑。

参数之间也能用 label 互相引用（`商品成本` → `param.cost`）。

实测：全部公式换中文写法后，GMV/成本/各项费用/净利与英文写法**完全一致**。

### 自动运行

新增 `src/auto_run.py`（should_run / build_range / describe_range）。
由**桥的守护线程**每 20 秒检查，到点往 `_PENDING` 队列塞任务，扩展来领。
为什么不放扩展：扩展的定时器只在浏览器开着、扩展没刷新时可靠；桥是常驻的。
扩展把 `auto` 标记透传到 /run，桥据此决定下载目录。

### 目录中文化的取舍

**代码包目录（src/bridge/scripts）不能改名**——那是 Python 的包路径，
改了所有 import 都得跟着改，收益远小于风险。
用户可见的目录（data/output/config/extension）改名，代价可控。

`paths._pick_dir(cn, en)`：中文目录不存在、旧英文目录存在 → 自动改名搬过去；
改名失败（被占用）→ 继续用旧目录，**绝不丢数据**。

发布目录顶层只留用户要碰的，代码副本收进 `_internal/源码/`。
踩坑：打包脚本是「逐文件覆盖」不删旧文件，导致上一版的 config/extension 残留，
用户会看到 config 和 配置 两个目录。修法：构建时先把上一版的旧目录名挪走。

### 顺带修的

- 报表用相对路径（rel）标识：不同店的报表可能重名，只按文件名会张冠李戴
- 批量下载打成 zip，zip 内保留店铺子目录
- loader.py 的 MAPPING_FILE 原来硬编码 `config/`，改成 paths.CONFIG

## 15:30 v0.21.1：公式更好写 + 款式编码列 + 费用占比列

用户提了 4 件事：
1. 公式里的分隔符换个符号（逗号分号都行），多候选改成「直接点添加多加一行」
2. 公式编辑不友好，看不懂怎么引用怎么写；优化完在程序里提示怎么写公式

4. 报表里要能看客单价、广告费比、发单费占比

### 公式引擎（src/formula.py）

**分隔符**：竖线 → 逗号/分号/换行都认（老的竖线配置照常能用）。
`compile_expr` 的 repl 里先把整段也当一个候选——有些列标题本身带逗号，
切开就找不到了。

**「本行X」概念**（关键设计）：
按**这一项自己勾选的订单类别**算的量。跟引用参数表里「订单数」那一行不是一回事。
发单费只算正常单时，它的「本行订单数」就只含正常单——两个口径可以不一样。

**费率名带「率」字**，参数表那行不带：
`platform_commission` → 「平台佣金率」，参数表 label → 「平台佣金」。
以前两者同名会撞车（费率名被当成了参数名，导致费率全是 0、净利算错）。

**别名优先级**（compute_params 里）：
1) 其它参数的中文名 → `param.<id>`（用 setdefault→直接赋值，压过内置量）
2) 费率项的中文名 → `params.<字段>`
3) 内置量的中文名 → gmv / paid / orders …
自己那一行的名字指向「本行」版本（自己引用自己没意义）。

**净利公式区也支持中文**：compute_formulas 加了 aliases 参数，
新加 FORMULA_CN（净利/毛利/费用合计/净利率），net_rate 能写「净利 / GMV」。

### 踩过的坑（重要）

1. **净利算成 0**：费率名和参数名同名，「平台佣金」被解析成了 `param.platform_commission`
   而不是 `params.platform_commission`。修法是费率名统一加「率」后缀。
2. **订单服务费差 24.84**：新配置写「订单数」，指的是参数表那一行（973 单，含样品）；
   旧配置写 `orders`，是按本项 kinds 现算（927 单）。改成「本行订单数」才对。
   **教训：涉及「按本项 kinds 算」的量，必须用「本行X」，不能用参数表那一行的名字。**
3. **UI 测试桩要跟真实实现对齐**：公式框从 input 改成 textarea 后，
   桩里 `value=` 塞多行内容会被当 HTML 空白吃掉，得先 innerHTML 再设 value。

### 款式编码（src/loader.py）

模板用数组公式 `TEXTJOIN("/",TRUE,UNIQUE(FILTER(链接资料!A:A,链接资料!B:B=商品ID,"")))`，
即「这条链接下所有 SKU 的款式编码，去重后用 / 连接」。程序用普通代码算。

**SkuIndex 加 by_product_styles**：商品ID → 款式编码列表（首次出现顺序，大小写不敏感去重）。

**根源问题**：店铺后台下载的链接资料表**没有款式编码列**（卖家自己加的），
所以 master.csv 里 style_code 全空。以前程序根本没读出来过。

**两条解法都实现了**：
- 有款式编码列就用它（模板工作簿那一列表头写「这列常态保留 勿删和覆盖」，
  加进列名别名就认出来了）
- 没有就从 seller_sku 推导：`derive_style_code()`
  规则 = 先试「字母前缀-字母+数字」两段式（MY-J68），再取第一个分隔符前的部分
  （V27-White-10Pcs → V27，V1【Set-LOVE】 → V1）
  实测 1377/1381 一致，剩下 4 行是表头说明行

**取的是「该链接全部 SKU」的**，不只是出了单的——模板查的是链接资料表，跟有没有出单无关。

### 链接资料：人工 + 自动两条路

- 人工：/api/link-info 接口 + 「店铺」页卡片
- 自动：扩展 runLinkInfo 任务 + 「取商品 SKU」时顺带存一份（同一接口，不重复抓）
- 扩展侧也实现了 deriveStyleCode（跟 Python 端同一套规则）

### 报表新增列

RATIO_ITEMS = [("dispatch","发单费占比"), ("ads","广告费比")]，
口径 = 费用 ÷ GMV（跟模板 J 列、AA 列一致）。
放在费用列后面，占比列位置随费用项数量变（c_ratio0 单独算）。

### 验证

- scripts/verify_styles.py（新增）：款式编码逐条核对模板 → 51/51 完全一致
- scripts/check_formula_ui.js（新增）：公式编辑交互回归测试
  （中文翻译、错词标红、订单表列、加一行按钮、英文老公式兼容）

- 打包版（按 exe 同级读配置的布局）实测：GMV 17352.29 / 订单数 973 / 净利 -96.31
